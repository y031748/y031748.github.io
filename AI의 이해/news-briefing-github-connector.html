GITHUB PUSH · 문제해결 일지

왜 자동 뉴스브리핑이 계속 GitHub에 안 올라갔을까?

"출입증을 다시 만들어주면 되겠지" 하고 시작했는데, 알고 보니 출입증은 처음부터 아무 상관이 없었어요. 총 8번의 시도 끝에 찾은 진짜 범인과, 그걸 찾아낸 과정을 순서대로 정리했어요.

추적 기록 — 8번의 시도

1

범인 지목 #1 틀림

GitHub 설정에서 Claude 앱의 "쓰기 권한"을 켜주면 될 줄 알았어요. 그런데 확인해보니 그 앱 자체가 계정에 설치조차 안 되어 있었어요.

Installed GitHub Apps → "No installed GitHub Apps"
2

범인 지목 #2 틀림

그럼 다시 연결(Authorize)하면 되겠지 — 했더니 "신원 확인"은 됐는데, 저장소에 접근하는 "설치" 단계는 여전히 비어 있었어요. 인증과 설치는 서로 다른 절차였던 거예요.

3

범인 지목 #3 틀림

그렇다면 직접 열쇠(개인 액세스 토큰)를 만들어서 쥐여주자 — GitHub에서 쓰기 권한이 있는 토큰을 새로 발급받아 클라우드 환경에 등록했어요.

4

여전히 막힘 403

새 열쇠로 git push를 해봤지만 똑같이 거부당했어요. 토큰 길이(93자)까지 확인해서 열쇠 자체는 멀쩡한 걸 확인했는데도요.

fatal: unable to access '...' The requested URL returned error: 403
5

범인 지목 #4 틀림

"아, 기존에 설정된 다른 인증 방식이 새 열쇠를 가로막고 있나 보다" — CI에서 쓰는 방식대로 인증 정보를 명령어에 직접 주입하는 방법까지 써봤어요. 결과는 똑같은 403.

6

결정적 단서 발견 단서

GitHub 서버에 직접 물어봤더니(API 호출), 진짜 이유가 나왔어요. 이건 GitHub가 아니라 Claude 쪽에서 보낸 메시지였어요:

"GitHub access is not enabled for this session. An org admin must connect the Claude GitHub App..."

즉, 우리가 만든 열쇠는 애초에 문에 닿지도 못하고 있었던 거예요. 다른 누군가(Claude의 대리 시스템)가 미리 문 앞에서 신분증을 대신 검사하고 있었던 거죠.

7

진짜 원인 확인 확인

공식 설명서를 찾아보니 확실해졌어요: 클라우드 작업 환경에서는 GitHub 인증서가 절대 작업 공간 안으로 들어오지 않고, 항상 Claude의 대리 보안 시스템이 대신 처리해요. 우리가 넣은 열쇠는 원래부터 쓰일 수가 없었던 거예요.

8

진짜 해결 성공

해결책은 아주 간단했어요. 터미널에서 /web-setup 한 번 실행 — 컴퓨터에 이미 로그인되어 있던 GitHub 계정 정보를 Claude 계정에 등록만 해주면 끝이었어요.

3f69f6e..0a30c46 main -> main (push 성공)

그래서 뭐가 문제였던 걸까요

건물 경비원을 떠올려보세요. 저는 계속 택배 기사(로봇)의 사원증을 새로 만들어주고 있었는데, 알고 보니 그 건물은 택배 기사 본인이 아니라 경비실이 직접 문을 열어주는 시스템이었어요. 사원증이 아무리 완벽해도 경비실에 "이 사람 들여보내도 돼요"라는 등록이 안 되어 있으면 소용없었던 거죠. /web-setup이 바로 그 "경비실 등록"이었어요.

뉴스 검색과 요약, HTML 제작까지는 처음부터 문제없이 잘 됐어요. 막힌 곳은 딱 한 곳, "완성한 걸 GitHub에 올리는" 마지막 한 걸음이었어요.
