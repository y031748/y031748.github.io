PR은 요청이고, 머지는 그 요청이 받아들여지는 순간

브랜치에 커밋을 쌓아도 그 자체론 main에 아무 영향이 없어요. PR(Pull Request)은 "이 브랜치 내용을 main에 반영해달라"는 요청이고, 머지(merge)는 그 요청이 실제로 받아들여져 두 역사가 하나로 합쳐지는 동작이에요. 방금 만든 PR을 예로 풀어볼게요.

브랜치가 갈라졌다 다시 만나는 모양

main은 계속 흘러가고, 작업 브랜치는 거기서 갈라져 나왔다가 PR과 머지를 거쳐 다시 합류해요.

main
claude/yesterday-discussion-review-bz9rnd
커밋 · twist-drill/index.html
머지 → main

왜 바로 main에 커밋하지 않았을까? PR을 거치면 머지 전에 변경 내용을 한 번 더 검토할 수 있고, 이 브랜치의 커밋들이 main 역사에 하나의 사건으로 명확히 남아요. 지금 이 PR은 아직 머지되지 않아서, twist-drill/index.html은 main에도, 실제 사이트에도 반영되지 않은 상태예요.

머지를 누르면 일어나는 일

1

두 역사를 비교

GitHub이 main과 작업 브랜치, 두 커밋 역사가 어디서 갈라졌는지 찾아요.

2

변경사항을 하나로 합침

작업 브랜치에서 쌓인 커밋들을 main 위에 적용해요. 충돌(같은 부분을 서로 다르게 고친 경우)이 없으면 자동으로 처리돼요.

3

main이 그 내용을 갖게 됨

머지가 끝나면 main 브랜치 자체가 twist-drill/index.html을 포함한 상태가 돼요. PR은 자동으로 닫혀요.

4

사이트에 실제로 반영

GitHub Pages가 main의 최신 상태를 다시 배포해서, 몇 분 안에 y031748.github.io/twist-drill/에서 실제로 열려요.

정리하면

  • PR은 "이 브랜치를 main에 반영해달라"는 요청이자 검토 단위예요. 그 자체로는 아직 아무것도 바뀌지 않아요.
  • 머지는 그 요청이 실행되는 순간이에요 — 두 브랜치의 역사가 합쳐지고, main이 그 변경을 갖게 돼요.
  • 머지돼야 비로소 GitHub Pages가 다시 배포되고, 실제 사이트에 반영돼요.
  • 지금 열려 있는 PR #1이 바로 그 대기 상태예요.
