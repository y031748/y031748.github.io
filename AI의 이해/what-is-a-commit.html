커밋, 변경 내용을 역사에 새기는 일

파일을 고쳐도 그 자체론 아무것도 기록되지 않아요. 커밋(commit)은 "지금 이 상태를 저장소 역사에 하나의 스냅샷으로 남기겠다"는 확정 동작이에요. 오늘 얘기했던 뉴스브리핑 업데이트를 예로 들어 그 과정을 풀어볼게요.

수정에서 반영까지, 세 번의 관문

파일을 고친다고 바로 기록되지 않아요. 세 단계를 순서대로 거쳐야 저장소 역사에 남고, 실제 사이트에도 반영돼요.

0

작업 폴더

파일을 열어서 내용을 고침. 아직 git은 이 변화를 "추적 안 함" 상태로만 인지해요.

news-briefing/index.html 수정
1

스테이징

이번 커밋에 포함시킬 변경사항을 고름. 장바구니에 담는 것과 같아요.

git add
2

커밋

담아둔 변경을 메시지와 함께 저장소 역사에 스냅샷으로 확정 기록.

git commit -m "..."
3

푸시

내 컴퓨터 안의 기록을 GitHub 원격 저장소로 올려서 사이트에 반영.

git push

커밋 하나의 구성

방금 이 저장소에 실제로 남은 커밋을 뜯어보면 이렇게 생겼어요.

해시
0a30c46
메시지
뉴스브리핑 2026-08-19
변경 파일
news-briefing/index.html
부모 커밋
3f69f6e
해시가 있는 이유 커밋마다 내용과 이전 커밋을 바탕으로 계산된 고유 ID(해시)가 붙어요. 메시지는 사람이 지어 붙이는 이름표일 뿐이고, 실제로 그 커밋을 가리키는 진짜 이름은 이 해시예요.

커밋이 이어지면 역사가 된다

각 커밋은 바로 이전 커밋을 "부모"로 가리켜요. 그래서 커밋을 죽 이으면 저장소가 지금 모습이 되기까지의 순서가 그대로 남아요.

be1d6b7
Add Bone Rising PWA and assetlinks.json
3f69f6e
Add .nojekyll to disable Jekyll processing
0a30c46
뉴스브리핑 2026-08-19
최신

정리하면

  • 커밋은 파일 변경을 저장소 역사에 남기는 확정 기록이에요. 사진을 찍듯 그 순간을 남겨요.
  • git add로 담고, git commit으로 기록하고, git push로 원격에 올려야 완성돼요.
  • 모든 커밋은 고유 해시를 가지고 이전 커밋을 가리켜서, 전체가 하나의 이어진 역사를 이뤄요.
